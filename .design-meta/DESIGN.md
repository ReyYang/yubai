### 数据算法与明确的实现选择

1. 当前锚点为 `Finance.funds.cash`，包含 archived 的现金／银行账户，按账户核对锚点加之后实际入账的变化求得。图画账户现金，不扣信用债务、存钱预留、未明确进账预留或始终留着，因而不等于还能花。
2. 历史含今天，今天取 `now` 的现金余额，之前每一天取当天结束余额。由后往前减去当天的现金净变动。核对锚点之前的流水参与倒推，不再次增加当前余额；已删除和尚未到入账时刻的流水不算。转账按每一侧实际 postingDate 记现金变化，同日现金账户间互抵，错日分侧；信用卡消费不动现金，现金还款／投资转出会动现金。工资收入及有关联的固定收付保留逐日事实事件。
3. 未来止于现有 `nextPayday`，无符合条件的固定收入时沿用 `Funds.horizonEnd`（默认 90 天）。复用固定收付的未付余额、跳过、停掉、估额和租金／分摊逻辑，发薪当天也包含。未来已关联流水在实际 posting 前不抑制安排。现金付款与收入到日阶跃，信用账户消费不立即扣现金，信用还款到日才扣；未指定账户的安排沿用原已知收付口径。
4. 今天实际点先保留，今天和过期未处理的收付在其后立即阶跃，不漏算，也不把它们写成过去已发生。未来每日扣原 `estimatedDailyLiving`。**Agent 实现选择**：范围为日常累计的 ±25%，固定收付平移上下界同等金额；这是情景范围，未经统计置信度验证，不是 owner 另行确认的概率模型。固定收付在同一 x 位置阶跃；净流入日先画收入阶跃，再计当天日常，避免工资前因画线顺序凭空多出一个低于每日余额的中间低点。最低取每日净收付后的点与今天实际点，并与实际绘出的曲线最低一致；不假设同日多笔固定收付的先后顺序。
5. 默认窗口起点为今天减两个日历月，终点为 horizon；总范围起点固定今天减三个日历月，导入一年也不延伸。拖动保持日历天跨度，起点夹在三个月前与默认起点之间，终点始终不超过 horizon。默认最低仅取含今天的预测；离开默认窗口后取当前窗口全部每日点，金额相同时取最早一天。始终留着只比较，等于目标不警示。

## 2026-11-03 · 导入整理恢复历史体积修复

来源为 owner 对真机导入4,200笔、整理一次后存储17.4 MB（恢复13.0 MB／20份、账本4.0 MB、附件398 KB）的反馈。本轮只改存储与整理保存行为、Core测试和记录，不改页面、样式或界面文案；没有读取用户真实账本。未读取、复制或写入设计稿链接，外部画布、旧原型与分发资源未同步。

根因：ImportOrganizer 每段 checkpoint 经 AppStore.apply → update → persist → LedgerRepository.save，后者无论 reason 是什么都先 preserveCurrent，把整本元数据 gzip 存入 Recovery。旧 pruneHistory 只有20份上限，没有天数或总字节限制；20是最终保留数，不代表一次只写20次。逐笔路径每段30笔，4,200笔可有140段；按对方路径的段数随分组变化。iCloud 上传还走另一次 save，且与本机镜像共用恢复目录。

已采用：beginImportOrganization 在提交运行前保存一次「导入整理」恢复版本，失败则不启动整理。该运行涵盖按钮选中的所有导入批次，完成／停下／失败一起结束；下一次重试重新留一份。apply 的 continuingImportOrganization 路径要求运行存在，将 preservingRecovery=false 传至 update／persist／save，保留校验、原子写入和版本检查，每段已完成ID、问题与批次撤销仍随账本保存。对应上传把同一策略随 pendingUpload 带到 synchronizeLedger，不因为异步上传晚于运行结束而再留快照；常规保存及其上传仍按原策略。运行持有整理前账本供即时撤销，中间段不再把撤销点推到最后一段之前。

恢复策略由 owner 授权补上总预算，具体数值为 Agent 实现选择：Recovery 整个目录最多10 MiB（10,485,760字节），含 gzip／旧 JSON、旧 sidecar 和共享 Payloads，仍最多20份，不新增按天到期。固定预算不随大账本继续增长，当前约0.6 MB的快照仍能保留十余份。保存恢复版本／普通保存后修剪，load 也修剪旧安装，先回收已无引用的共享附件，再从最旧版本删除并重算实际文件长度；至少保留最新一份。最新文件损坏时也保留最后可读版本；任何保留元数据无法读取时不猜测删除共享附件。最新恢复版本或当前账本必需的共享附件本身超预算、元数据不可读或文件删除失败时，保留恢复能力优先，可能超过预算；不会为了压到固定数字删掉最后的可恢复资料。

账本检查：Entry 没有整份原始行数组或嵌套账本，原件按批次附件单独保留；note 含备注／对手／状态／付款方式，title／purpose 分别保留原始名称和整理用途。sourceIdentity、externalID、fingerprint 服务跨来源去重与合并后的来源追踪，未删。organization 只累计一份 ChangeSet 明细，供现有导入详情展示；未用删历史明细改变页面行为。新增 Entry.encode 只省略解码器已有默认值的空字符串和默认标志，所有事实及非默认值保留，不改 schema。

ImportOrganization.recordUndo 原本已是 diff：只存被改动的其他批次条目的最早前值，以及新增计划／卡片／记忆ID；本批条目整批撤销时移除，未存整个 before Ledger。本轮将已记录条目ID改为 Set 检查，避免每段反复线性查找，并验证跨段重复改动只保留第一次前值。没有引入新 undo 格式或抛弃旧 undo；旧 Entry 全字段、旧 undo 缺 memoryIDs 的格式均可读回、再保存、整批撤销。更早且本来没有 undo 的批次沿用原有软删除路径，没有新增旧批次能力损失。

## 从真实任务开始

用户场景：每周集中整理多个渠道账单，日常可补充截图或手工记录，希望减少维护负担。朋友按月转来房租分摊、用户按季度付租，使账户余额不能直接代表可花金额。事实来源：[地图 Notes](../.scratch/yubai-product/map.md#notes)。

当前局部任务：**一批记录整理结束 → 用户看摘要，可直接离开，也可补充用途或批量纠正 → 系统显示结果并保留可恢复入口 → 用户不必逐笔审核即可结束这次整理。**

采用边界：自动分类、只询问特别不明的记录或放入其他，是已确认方向；具体摘要、分组补充、返回路径和撤销呈现属于[导入结果原型](../.scratch/yubai-product/issues/12-import-result-prototype.md)候选。导入解析、去重、资金核对与真实保存尚未实现，规则见[多入口记录](../.scratch/yubai-product/issues/04-import-and-reconciliation.md)。

原型输入是合成汇总：3,972 条明确记录、26 条其他支出、2 条用途未知，共 4,000 条，仅展开代表记录。不能据此推断 AI 准确率、耗时、真实数据分布或完整交易处理能力。

## 指导取舍的原则

| 保护的体验 | 因此怎样设计 | 适用边界与来源 |
|---|---|---|
| 一次整理可以轻松结束 | 默认自动归类，普通细类未知允许归其他，纠正入口按需展开 | 不把性质不明当成确定收入；方向来自地图，具体分组与退出方案待反馈 |
| 理解钱实际能做什么 | 区分账面进出、用途与未来义务；待规则明确后展示依据 | 不自行编造可花金额公式；[资金票](../.scratch/yubai-product/issues/02-funds-and-obligations.md)未解决 |
| 资金安排跟着现实变化 | 从当前时间和已知付款日期推演，保留实际租金日期 | 固定账单导出区间仍可用于筛选；不因此固定资金管理周期 |
| 用户容易纠正系统 | 建议展示影响范围、支持批量修改和撤销，金额由用户修正 | 撤销持久性仍是候选；AI 不以“整理”名义改金额 |
| 补充的是钱的用途 | 用自然语言问这笔钱做什么，允许少量未知 | 必要字段见[云端边界票](../.scratch/yubai-product/issues/01-cloud-data-boundary.md)，姓名留本地的方向不代表具体外发字段已获批准 |
